## 2. 完整性清单失败：根因与修复（本会话）

- 现象：81910d2 声称「33/33 自检通过」，但 HEAD 上 `app_server.py` / `history_db.py` / `routes/config_routes.py` / `routes/task_routes.py` 四模块哈希失配（1001 passed / 1 failed）。
- 排除项：非行尾问题（`.gitattributes` 强制 LF，磁盘哈希 = git blob 哈希，均 ≠ 清单期望值）；非篡改。
- 根因：清单 `generated_at=13:01:40` 按**变更前**代码树生成；13:07-13:08 功能提交修改了上述 4 个文件；13:09 一并提交时清单已过期。「33/33 通过」在生成时点为真、在提交时点为假——属「生成与提交之间发生代码变更」的流程缺陷。
- 修复：工作树干净（无 WIP）前提下按 HEAD 重生成清单；diff 仅 `generated_at` + 4 个哈希；`TestIntegritySelfCheck` 恢复绿色。
- **防复发建议（P2）**：① 清单重生成必须放在同一提交全部代码改动之后、提交之前执行；② CI 增加一步「按检出代码重算哈希 ≠ 入库清单即 fail」的门禁断言（与 `check_config_refs.py` 同级），彻底消除"清单过期入库"这类静默失配。
- 附注：生成脚本以文本模式写文件（Windows 下 CRLF），提交时经 `.gitattributes` 归一为 LF；自检端哈希前剥离 `\r`，两端语义兼容。建议生成器改二进制写（`open(..., 'wb')` + LF）以消除平台差异。
